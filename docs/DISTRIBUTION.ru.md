# Распространение каталога и совместимость

[English](DISTRIBUTION.md)

> **Историческое проектное предложение, а не реализованный контракт релизов.** Релиз с ZIP отобранных данных уже существует; описанные ниже индекс, отдельные пакеты схем и обновление клиента этим релизом не подтверждены. См. [действующую политику релизов](../.github/RELEASE_POLICY.ru.md).

## Цели

1. Распространять неизменяемые снимки через **GitHub Releases**.
2. Позволять конкретной версии аддона Filamentra устанавливать новейший каталог, который она может разобрать.
3. Не требовать токен для публичных загрузок.
4. Сначала загружать кешированный снимок; не блокировать палитру сетевым доступом.
5. Никогда не изменять установленные внешние виды в сохранённых моделях только потому, что изменились исходные данные.

## Независимые версии

- **SemVer каталога**, например `1.2.0`: поставляемые записи производителей, линеек и цветов.
- **Целое число схемы**, например `1`: структура JSON-записей.
- **SemVer аддона**, например `0.5.0`: реализация клиента, развивающаяся отдельно.

Обычные добавления и исправления могут использовать ту же схему; несовместимые структурные изменения требуют новой схемы. Аддон объявляет версии схем, которые понимает.

## Предлагаемые файлы релиза

Стабильный релиз `v1.2.0` мог бы содержать:

```text
catalog-index.json
catalog-schema-v1.zip
```

Если будущий выпуск поддерживает несколько поколений схем, он может включать `catalog-schema-v1.zip`, `catalog-schema-v2.zip` и т. д. Старые выпуски каталога остаются доступны как резервные.

Пакет `catalog-schema-vN.zip` содержит версионированный автономный снимок `catalog/brands/` и соответствующую схему. Аддон никогда не должен загружать необработанные файлы из `main` как рабочий источник: ветка не является неизменяемым снимком.

## Предлагаемый индекс

Новейший стабильный GitHub Release включает индекс **всех сохранённых совместимых вариантов релизов**, а не только собственных файлов.

```json
{
  "index_schema": 1,
  "releases": [
    {
      "version": "1.2.0",
      "tag": "v1.2.0",
      "variants": [
        {
          "schema": 2,
          "min_addin": "0.8.0",
          "asset": "catalog-schema-v2.zip",
          "sha256": "<64 lowercase hexadecimal characters>"
        },
        {
          "schema": 1,
          "min_addin": "0.3.0",
          "asset": "catalog-schema-v1.zip",
          "sha256": "<64 lowercase hexadecimal characters>"
        }
      ]
    },
    {
      "version": "1.1.0",
      "tag": "v1.1.0",
      "variants": [
        {
          "schema": 1,
          "min_addin": "0.3.0",
          "asset": "catalog-schema-v1.zip",
          "sha256": "<64 lowercase hexadecimal characters>"
        }
      ]
    }
  ]
}
```

**Значения выше приведены для примера и не являются опубликованными релизами.** После реализации контракта документируйте точные границы совместимости и развитие схемы индекса. Если аддон не понимает текущий формат индекса, он должен использовать проверенный кеш каталога, а не делать предположения.

Предполагаемый публичный адрес индекса:

```text
https://github.com/4FusionLab/Filamentra-DataSource/releases/latest/download/catalog-index.json
```

Когда релизы появятся, аддон сможет скачать выбранный файл по тегу релиза:

```text
https://github.com/4FusionLab/Filamentra-DataSource/releases/download/<tag>/catalog-schema-v1.zip
```

`latest` в GitHub указывает на последний подходящий стабильный выпуск, но не обязательно на все предварительные выпуски или черновики.

## Обновление клиента

1. Сразу открыть последний проверенный кеш.
2. Не чаще настроенного интервала обновления загрузить новейший индекс с короткими тайм-аутами; предложить ручное обновление.
3. Разобрать и проверить индекс. Отфильтровать варианты по поддерживаемой схеме и диапазону совместимости аддона.
4. Выбрать новейший совместимый **релиз каталога**, затем предпочитаемую поддерживаемую схему.
5. Если он уже кеширован, ничего не делать. Иначе скачать точный файл релиза.
6. До активации проверить SHA-256, максимально допустимый размер, ожидаемые пути архива и каждую JSON-запись.
7. Распаковать во временный каталог с защитой от выхода за пределы каталога через пути ZIP; после успешной проверки атомарно активировать новый снимок.
8. Сохранить предыдущий корректный снимок для отката. При любой ошибке сети или проверки продолжить автономно с кешем.

Не изменяйте незаметно установленные пользователем Fusion Appearances: обновление каталога и обновление Appearance в модели — разные действия.

## Планируемый конвейер публикации

При теге релиза:

1. Проверить все записи производителей и линеек по схемам.
2. Проверить целостность ссылок, повторяющиеся идентификаторы, происхождение цветов, URL источников и ограничения лицензирования данных.
3. Собрать детерминированные ZIP для поддерживаемых вариантов схем.
4. Вычислить контрольные суммы.
5. Создать индекс, сохранив записи прошлых релизов, которые остаются корректными и доступными.
6. Опубликовать файлы релиза и только затем предоставить полный индекс через новейший выпуск.

Предложенный конвейер публикации с индексом ещё предстоит реализовать и проверить. Существующий CI публикует ZIP отобранных данных по действующей политике релизов; это не подтверждает предложенный контракт индекса совместимости.

## Доступ и учётные данные

Репозиторий сейчас **публичный**, поэтому публичные файлы релизов можно скачивать без встраивания учётных данных в аддон. Если данные потребуется закрыть, понадобится токен GitHub или аутентифицированный прокси. Не поставляйте токен доступа к репозиторию внутри аддона.
